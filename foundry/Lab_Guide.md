# Hands-on lab: build a small C# support agent

**Duration:** about 30 minutes after the README setup and model download.  
**Technology:** .NET 10, Foundry Local, the official OpenAI C# client, Microsoft.Data.Sqlite, and one small local model.  
**Scenario:** fictional Lighthouse Credit Union support.  
**Cloud:** not required for this lab. The separate instructor demonstration takes about five minutes.  
**Follow-up:** an optional 20-minute exercise adds a sentiment-analysis tool after this core lab.

## What you are building

The agent answers a member's support question using a small SQLite database on your computer. Its one tool is a normal C# function. The model requests that tool by name; the application runs a fixed query and returns the retrieved articles to the model. The model then writes the answer.

This gives you a complete, visible agent loop in one console project:

1. Send the user's message and the available tool definition to the model.
2. Receive a tool request selected by the model.
3. Run the allowed C# function, query the local database, and return the rows using the matching tool-call ID.
4. Ask the model to finish its answer.

The tool opens SQLite in read-only mode and retrieves the 12 small articles from `knowledge_articles`. It cannot change those articles, inspect an account, freeze a card, submit a case, or contact a support representative. All supplied details are fictional.

Keep your terminal in the **`App` folder** throughout this guide. File names below refer to files in that folder. SQLite needs no separate installer or database server for this lab.

## Activity 1: run and observe | 5 minutes

Complete the [README](README.md) setup, keep exactly one tools-capable `qwen2.5-0.5b` model loaded, and run `dotnet run` from `App`.

Confirm the startup banner identifies the **Local** provider and prints `Knowledge database:` followed by an absolute path to `support.db`. The app creates this database from `seed.sql` when it is missing. Normal runs reuse the existing database. Ask:

```text
Use your support information tool to tell me Member Care's Saturday hours and time zone.
```

Observe this tool-call marker before the final answer:

```text
[tool] get_support_info -> querying SQLite support.db
```

Compare the response with the supplied schedule: Saturday 09:00 to 13:00, America/New_York. You will inspect the actual database rows in Activity 4. Wording can vary. The facts and actual tool use are what matter.

**Checkpoint:** explain which part ran in C# and which part was generated by the model. The model proposes the tool call; the C# application controls what actually executes.

## Activity 2: read the agent and its query | 5 minutes

Open `Program.cs` and `KnowledgeStore.cs`. Find these elements:

| Element | What to notice |
|---|---|
| Agent instructions | The system message defines the support role and capability limits |
| Tool definition | A name, a description, and a zero-argument schema tell the model what it can request |
| Tool execution | The app allows only `get_support_info`; the model supplies no SQL or database path |
| Database query | `KnowledgeStore.cs` opens SQLite with `Mode=ReadOnly` and runs a fixed `SELECT` for article ID, title, and content |
| Conversation loop | An assistant tool request and its matching tool result are added before the next model call |

The query retrieves all 12 articles because this dataset is deliberately tiny. The tool serializes those rows as JSON to send them in the model's tool-result message. The stored knowledge lives in SQLite.

The application bounds repeated model/tool turns. It also reports an incomplete response rather than presenting it as a successful answer. You do not need another framework or an Azure service to see these mechanics.

**Checkpoint:** point to the code that prevents the model from executing an arbitrary C# function. A function name in model output is not permission to run arbitrary code.

## Activity 3: change the agent's style in C# | 5 minutes

1. Exit the console app.
2. In `Program.cs`, locate the comment **LAB 1: Change the agent instructions**.
3. Replace **Answer from its result in no more than three short sentences.** with **Answer from its result in three short bullet points.** inside the existing instruction string.
4. Save the file and run `dotnet run` again. This rebuilds your edited C# project.
5. Repeat the exact Saturday-hours prompt.

Compare the answer's presentation and its facts. The instruction changes how the model is asked to respond; it does not rewrite the support data. If the small model ignores the formatting request, record that observation. Do not mistake a fluent response for reliable instruction following.

**Checkpoint:** the tool still runs, the supported facts remain correct, and you can identify the changed C# instruction.

## Activity 4: inspect and update the local knowledge | 10 minutes

### Inspect the current database

Enter `/exit`, then run:

```text
dotnet run -- --show-knowledge
```

The command prints the absolute database path and queries the stored rows, displaying them as formatted JSON. It then exits. It requires no model call or Azure credentials.

Find the `member_care` article and confirm its original Saturday hours. The table has three text columns: `article_id` (the primary key), `title`, and `content`.

| Article ID | Knowledge it supplies |
|---|---|
| `member_care` | Contact number, opening hours, and time zone |
| `card_security` | Lost-card contact route and 24-hour availability |
| `digital_banking_login` | Recover-access guidance without collecting secrets |
| `mobile_check_deposit` | Fictional eligibility, per-check limit, and daily limit |
| `deposit_review` | Review cutoff and the distinction from funds availability |
| `internal_transfers` | General internal-transfer guidance and action limits |
| `statements` | Statement access and the fictional retention window |
| `branch_appointments` | Appointment windows and booking guidance |
| `accessibility_support` | Accessibility and language-support requests |
| `complaint_followup` | Acknowledgement timing without a resolution promise |
| `capabilities` | Actions the agent cannot perform |
| `training_notice` | Fictional organization and nonworking phone-number notice |

### Make one controlled change

1. Open `seed.sql`. In the `member_care` article, change only **09:00 to 13:00** to **10:00 to 14:00**. Keep the surrounding SQL quotes and punctuation intact.
2. Save the file and run `dotnet run -- --show-knowledge` again. The stored hours are still **09:00 to 13:00**. **Editing the seed alone does not change an existing database.** Normal runs read `support.db`; the seed is used only to create a missing database or when you explicitly reset it.
3. Reload the synthetic lab knowledge and inspect it:

```text
dotnet run -- --reset-db
dotnet run -- --show-knowledge
```

The reset command prints `Knowledge reset from seed.sql.` and exits. It replaces the lab's `knowledge_articles` table with the seed contents. This explicit command is separate from the read-only tool available to the model. Check that the inspected `member_care` row now contains **10:00 to 14:00**.

4. Run `dotnet run` again and repeat the Saturday-hours prompt in the new conversation.
5. Verify the SQLite tool trace and the changed hours in the answer. Confirm that the displayed database path matches the one you inspected.

This demonstrates knowledge retrieval at inference time. You changed the stored information and supplied new query results to the model; you did not retrain it. Starting a fresh process also removes earlier conversation history from the comparison.

### Restore the original knowledge

Enter `/exit`. Restore **09:00 to 13:00** in `seed.sql`, save, and run:

```text
dotnet run -- --reset-db
dotnet run -- --show-knowledge
```

Confirm the original hours are back in the database, then run `dotnet run` to continue.

If the answer retains old hours, use `--show-knowledge` to check the actual rows first. If those are old, confirm the seed edit and explicit reset. If the rows are correct, check the tool trace and use a fresh conversation. Record any remaining model failure instead of treating fluent wording as proof of correctness.

## Activity 5: check the boundary and explain the switch | 5 minutes

Ask these separately. Enter `/reset` between independent checks to clear the conversation. This chat command leaves the database unchanged; `--reset-db` is a separate terminal option that reloads the synthetic knowledge after you exit the agent.

```text
I lost my card. Which support channel should I use?
```

```text
What is my current account balance?
```

For the lost-card question, look for the fictional Card Security route, its 24-hour availability, a training-placeholder label, and no claim that a card was frozen or a case created. For the balance question, the agent should explain that it has no account access. It must not invent a balance.

Then open `appsettings.json`. Find `Provider`, currently `Local`. The optional instructor demonstration changes it to `Azure` after Azure's endpoint, deployment name, and process environment key are prepared. The C# agent, tool, and SQLite database remain on the computer. Only inference moves to the cloud; the retrieved rows are sent to the cloud model as tool-result content.

## Five outcome checks

Use **Pass**, **Needs correction**, **Blocked**, or **Not run**. These are blank records for your actual results.

| Check | Expected evidence | Your result |
|---|---|---|
| 1. Local agent | Local banner, real tool marker, correct original Saturday hours and time zone | Not run |
| 2. C# edit | Rebuilt app uses the edited instruction; any formatting limitation is recorded | Not run |
| 3. SQLite knowledge change | Inspection shows changed stored hours after reset; the tool uses them in a fresh run; both seed and database are restored | Not run |
| 4. Urgent support | Correct fictional Card Security route, no account action claimed | Not run |
| 5. Account boundary | No invented balance, account lookup, or transaction | Not run |

If a tool was never called, the tool-use objective is still incomplete even if the answer happens to be correct. Fix or disclose observed failures. Small-model behavior must be rehearsed on the actual workshop device.

## Microsoft grounding

The tool loop follows the documented Foundry Local tool-calling pattern. The local HTTP server and Azure resource endpoint both expose Chat Completions, which is the shared interface used for this demonstration. SQLite access uses the [Microsoft.Data.Sqlite provider](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/) and its documented [read-only connection mode](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/connection-strings). Current source links and the package's verification record are in [Sources and Validation](Sources_and_Validation.md).
